# Orleans Activity streaming

Orleans provides nonblocking admission of Activity token batches to a live, activation-owned Activity network. `Accepted` means the runtime accepted responsibility for the whole batch; it does not mean that its nodes have completed. The activation retains the live marking and values while the stream is busy and persists them when the network reaches natural quiescence or a checkpoint completes.

```csharp
var result = await activity.StreamInputAsync(tokens => tokens.Add(order));
if (result.Status != EventStatus.Accepted)
{
    // Retry or apply backpressure; the input was not admitted.
}
```

`StreamInputAsync` adds the `Stream` header and submits a `TokensInput` send. `Stream` is valid only on token-input events and only on Orleans; other runtimes reject it. A token request (`RequestAsync<TokensOutput>(TokensInput)`) is not a stream send and is rejected while a stream is active.

Every Orleans Activity event, regular or streamed, is executed by one activation-owned session: a single retained Activity executor, marking, and service scope. Without an active stream, a regular call keeps ordinary transactional semantics: its changes commit when it succeeds and are rolled back when it fails. A regular event that is already running when the first stream input arrives shares the same executor and marking with that input; only its rollback semantics switch to the streaming busy period, and its pure branches keep their transactional provenance. A later input can start while another firing is awaiting asynchronous work. Regular Activity events can also be handled by the live network during that firing; their changes to `Behavior.Values` are immediately visible to it. A node is serialized by default while its firing is active. Set `NodeOptions.Reentrant` on an action node when that node is safe for overlapping firings; each firing receives its own input snapshot and DI scope.

The admission bound is `StateflowsRuntimeOptions.MaxQueuedActivityStreamEvents` (default `128`), counting queued and running batches. When the bound is exhausted, the complete new batch is rejected as `Overloaded`. Orleans resource leases remain held until admitted work finishes or is discarded. Stream admission is volatile until a checkpoint: a crash can lose admitted but uncheckpointed work.

On a cold Activity, Orleans rejects stream admission if typed initializers are configured. Otherwise the default/implicit initializer must complete successfully before `Accepted` is returned. Initialize typed-initializer Activities explicitly first. Stream admission does not create an event receipt, so application-level token identity is needed if callers retry after an uncertain network failure.

Each routed token occurrence keeps its own provenance (transactional or streamed), including forked routes, control tokens, and structured/iterative/parallel scopes. Initial, accept-event, time-event, and regular-input sources are transactional, including accept-event and time-event firings delivered by the live timer pump while a stream is active; a firing that consumes any streamed token is streamed, and so are all of its outputs. Each regular call owns one transaction. The transaction stays open while its own firings, guards, transformations, and enabled successors are running; idle tokens waiting for missing input do not keep it open. When a regular firing enables a successor that also consumes streamed tokens (a mixed acceptance), the transaction hands that successor off to the live stream and completes without waiting for it or its streamed descendants. A data store converts transactional arrivals to streamed work during a streaming busy period, so routing into a data store is a handoff as well. Inside a structured/iterative/parallel scope the same handoff applies: the transaction finishes its pure branches, the enclosing invocation is recorded as a continuation, and the live stream continues it (without rerunning its initializer, continuing unstarted partitions, and running its finalizer once). A pure transactional branch that is already running when the first stream input arrives keeps its transactional color. Once the transaction closes, its remaining idle tokens are recolored as streamed. Values and marking are shared live state during streaming: individual value operations are synchronized, but a sequence of operations is not isolated or rolled back. Streamed and mixed firings publish immediately. Publications from regular-only firings are held until their regular call commits and are discarded if it fails. Failures do not undo effects already applied to the live session.

`Checkpoint` (a header on a regular call) requests a firing-boundary barrier. New stream inputs are held for the next epoch and no new firings start. Active node bodies finish; their outputs are routed into the marking and recorded as ready firings without being started. The requesting regular event's transactional part runs against the same live context, and the snapshot is committed with that call. The network then resumes from those ready firings. The snapshot does not serialize .NET tasks or stacks. Instead, each ready firing records its node, upstream edge, execution thread, and selection tokens; resumed firings inside iterative/parallel partitions expose the partition selection through the typed token context exactly as in a continuous run. Each suspended structured/iterative/parallel invocation records a continuation frame with its original input, the remaining (`RestOfInput`) tokens, its started and completed partitions, and the output accumulated so far. On resume, a structural node does not rerun its initializer, starts every ready sibling firing, continues the unfinished partitions, and runs its finalizer once. When a grain activates with checkpointed ready work, it resumes that work before serving the next call, and idle tokens stay idle. `StateflowsRuntimeOptions.ActivityStreamBarrierTimeout` defaults to infinite; when configured, a timeout fails that regular call, drops its deferred publications, releases the barrier, and leaves live effects intact. Do not treat an admitted batch as a durable job until a checkpoint has succeeded.

To checkpoint without delivering another event, send `new ActivityCheckpoint()` or use `await activity.CheckpointAsync()`. This standalone event uses the same barrier, timeout, persistence and resumption semantics as the `Checkpoint` header, but does not inject tokens, run accept-event nodes or implicitly initialize an idle Activity. A successful send returns `EventStatus.Consumed` after the snapshot commits. Like the header, it is supported only by Orleans Activities.

An unhandled streamed invocation failure is logged and emits an immediate `ActivityStreamFailure` notification containing the Activity ID, triggering event ID/name, and exception types. The failed invocation is isolated from other admitted work; effects already made against the live session are not rolled back.

`IExecutionContext.ExecutionMode` describes the current invocation, not the whole Activity busy period. Pure transactional and accepted-event/time-event invocations report `ExecutionMode.Transactional` and retain their event metadata. Streamed/mixed invocations, including ready work resumed after a checkpoint, report `ExecutionMode.Streamed`: `ExecutionTrigger`, `ExecutionTriggerId`, and `Headers` are null. There is no synthetic trigger or single source-event lineage for token-enabled execution. Use the Activity input-token APIs for the firing's data; use typed event contexts for an actual accepted event. Invocation metadata is scoped independently across concurrent asynchronous work and retained by the invocation context.

`FinalizationMode.Queued` waits for earlier regular calls, then stops further admission, discards not-yet-started stream batches, cooperatively cancels active node scopes, and finalizes after active invocations drain; it does not wait for natural stream exhaustion. `FinalizationMode.Immediate` acknowledges a cancellation request with `Cancelled`, stops admission, cooperatively cancels active node scopes, and finalizes after active invocations drain. Late engine effects from a replaced generation are fenced. Non-cooperative user code and external side effects already started cannot be forcibly stopped.

Value mutations through a cancelled Activity scope are ignored, including updates, removals, and clears; values written before cancellation remain visible to the finalizer. A reset clears Activity values and marking. Use `Checkpoint` on a reset during streaming to wait for active firing bodies to finish and discard their ready successors at the barrier before the network resumes.

## Known limitations

- Stream admission and live timer schedules are volatile until a checkpoint commits: a crash can lose admitted but uncheckpointed work.
- External side effects of non-cooperative user code cannot be fenced or rolled back; engine effects (values, marking, publications, outputs) of cancelled or replaced work are fenced.
